How this was built

Eight hours across six days, in five or six short sessions — which matters, because almost every removal here happened because I left it alone and came back. And not one prototype: three, the third a deliberate merge of the first two.

V1 · 30 Jul

Full depth, and too complex to pitch: evidence, basis, score, confidence, risk tolerance, transition type and usage assumption — seven weighting concepts to reach one call.
V2 · 30 Jul

Built by Claude Code with no steering, as a check on my own judgement. Simpler, weaker underneath, and right about two things I had over-built.
V3 · 31 Jul → 2 Aug
Shipped
~60% of V1, a little of V2, and a lot of subtraction — stripped until it was explainable in a seven-minute pitch.
The rule I cut against. Every keep / drop / add was scored on one question: does this help the customer take the decision? Not "is it clever". That is why a working risk engine came out and the evidence model stayed.

The honest AI story is here, not in a claim about tooling. An agent produced real depth fast — and a decision model with more moving parts than the problem needs. The stripping was the work, and that judgement is not something the agent supplied.

What I built

  • A Context Slice page — load four files, see what they can and cannot support. Matched by column signature, not filename: a Basis team exports ZOBJ_DUMP_PRD1_0714.CSV, never objects.csv.
  • A rules engine, not a model. Twelve ordered rules, first match wins, weights in one editable file — so "why retire?" is answered with a named rule and the customer's own rows. Five calls: Remediate Investigate Workshop Retire Carry as-is.
  • A four-state evidence model — the spine. Measured and running, measured at zero, never measured, cannot be measured. Only the first two are observations.
  • The Landscape Footprint — eleven decisions as a treemap and a list, each opening onto its objects, its blast radius, and an editable call.
  • One control that changes the answer — the transition path. It reorders, and in seven of forty-four combinations it changes the call and says why.
  • A Discovery Agent explaining either page for the board, the programme or the engineer — composed from live numbers each time, and marked wherever it appears.
  • A verification harness re-deriving every headline number from the raw files.

What the data changed about the design

  • I profiled all four files before designing anything. The shape came from the data, not from a guess about what would look good.
  • The finding that reframed everything: 207 objects have no usage row, which reads as fatal until you split it — 61% of SAP's own code is unmeasured against 16% of the custom code, and every object measured at zero is custom. The blind spot is in code nobody was deciding about.
  • Three transaction codes point at programs the inventory does not contain — one runs 3,860 times a month across 74 users. Runnable today, owned by nobody.
  • SAP's own code never calls custom code — not once in 326 dependencies. What stops you retiring is people using it, which is far easier to check.
  • I rejected the obvious dead-code test. No usage, no callers, no callees → 105 objects, 101 of them SAP's. Everything scores on converging signals instead.
  • The evidence basis is load-bearing. Retire is reachable only from a fact or a measurement; inference and absence propose Investigate and name what would settle it.
A number worth stating carefully. "52 of 106 custom objects run zero times a month" is three findings in one coat: 17 measured at zero, 17 never measured, 18 tables that cannot carry an execution count. Collapsing them is the fastest route to a confident, wrong retirement list — hence four states, not two.

Bugs worth recording

  • A split cache, twice, on the deployed copy only. Pages caches each file for ten minutes independently, so a new page sat beside a stale module and died on boot — and the handler blamed the local server, the one thing that was fine. Versioning the entry alone let it recur. Fixed with an import map pinning all thirteen modules.
  • The sharper half: the data files were unversioned too, so a stale rulepack.json would have produced yesterday's weights — wrong rather than old, and silently. They now revalidate.
  • The treemap rendered blank on first view — it measures a container with no box while hidden, and ResizeObserver does not fire for display:none → visible.
  • Controls that rebuilt on every render detached the button under the cursor, so clicking looked like it did nothing. Sorting by call opened backwards.

Two hours forty over, all found by rehearsing rather than building. Forty reordered the Footprint and gave three Scope cards their evidence. What the split says. Nearly a third went to planning and pivoting rather than building, including throwing most of V1 away. On a hard cap that is the uncomfortable allocation, and the one I would make again: the build was fast; choosing what not to ship was expensive.
