Deliverable 3 · Deployment Design

The first four weeks with the real customer

Who I need, what access, the first milestone that proves value, and what would make me stop.

Customer: SAP ECC, three productive systemsPosition: step 0, before the SI is selectedGoal: a scope decision, not a tool install

Weeks 1–4 are not about deploying software — the prototype already runs, with no install and no production connection. They are about converting the footprint into decisions the customer will stand behind, and being equally clear about which the evidence does not yet support. I assume the system integrator is not yet selected, making this step 0: a small, separately funded discovery that sharpens scope before anyone bids. If an SI is already in place, we run alongside them instead of competing for their assessment.

What access

Deliberately low, so the bar to start is near zero: read-only metadata extracts — object inventory, usage statistics, dependencies, and the transaction-to-program map — for all three productive systems. No source code and no production connection, so we can start before security review completes. One non-extract ask on day one: start a usage collection (SCMON / UPL) if none is running — it needs a full business cycle, and unlocks more undecidable objects than anything else we could do.

4 · Prove valueSteering readout: what is decided, what is held, what it costs to resolve the rest.Milestone, below
First milestone (end of week 4): a business-signed decision position — and, underneath it, the seeded technical layer of a Context Model. The position is what the sponsor signs; the Context Model is what makes the position repeatable next quarter and on the other two systems. Not a report. On the sample extract that is 24 of 106 custom objects with an action against them — 13 retirements on measured evidence, 6 objects remediated before they block a clean core, 5 into a fit-to-standard workshop — alongside 34 explicitly held, each naming the evidence that would settle it. Nothing in that first number rests on anything weaker than a measurement, which is what makes it signable. Two numbers, not one: what we act on now, and what it costs to decide the rest.
Why not a bigger number. It would be easy to claim half the custom estate is retirable — 52 of 106 objects are not measurably running. But that merges three findings: 17 measured at zero, 17 never measured, and 18 tables that cannot carry an execution count. The smaller number is the one that survives someone checking it.

What would make me stop

  • Access will not come. No consistent extracts across all three systems within ~2 weeks and the footprint is partial and quietly misleading. Pause rather than decide on a fraction of the landscape.
  • Usage data is missing or untrustworthy. Then this is a measurement project first, and I would say so rather than dress inference up as evidence.
  • Nobody will sign off. If no one will approve a retirement, we are producing a report. That is an organisational problem a tool cannot fix.
  • The transition type is locked without evidence. If a partner has fixed greenfield or brownfield and the customer will not reopen it, most of the value — showing what each path costs — is gone.
  • They already have something they trust. Then we redirect to where we are additive rather than rebuild what exists.
