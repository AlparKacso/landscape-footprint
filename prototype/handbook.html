Landscape Footprint

A company is about to move off SAP ECC. Before anyone can plan that, somebody has to answer a boring, enormous question: what is actually in there, and what do we do with it? This turns four spreadsheets of system data into eleven decisions a leader can fund — each one showing the evidence behind it and how much to trust it.

Data 4 files, one ECC system Objects 366 · 106 custom Decisions 11 Setup none

What it is

The obvious thing to build from a list of system objects and their connections is a big network diagram. It looks impressive. Nobody can act on it, and it is exactly the kind of picture the Celonis vision paper argues against.

So this is a list of decisions instead of a picture. Each one says what to do, why, and how confident you should be. A diagram does appear — but only inside a single decision, answering one question: if we do this, what else moves?

Key Nothing is recommended by AI. Every recommendation comes from a set of written rules you can read and re-run. The Discovery Agent writes words — the summaries, the sentence that opens the Landscape Footprint, and the explanation of either page — and everything it wrote is marked Discovery Agent generated insight, saying which part is the agent's. The wording is; the numbers inside it are not. That way, when someone asks “why does it say retire?”, the answer is a rule and rows from their own data — not “the model said so”.

The two pages

They do different jobs, so they are kept apart. One is how the answer gets made; the other is the answer.

The Extract Wizard

Four steps. The point of showing them is trust: a tool that swallows your data and returns confident advice is asking to be believed. One that shows its working can be checked.

01

Load your files

Drag in the CSV files your Basis team exported. Nothing is cleaned or corrected on the way in — the messy parts of an export are usually findings, not mistakes to tidy away before anyone sees them.

The tool works out which file is which by looking at the column headings, not the filename. That matters because a real export is called something like ZOBJ_DUMP_PRD1_0714.CSV, never objects.csv. Each file shows what it matched on and what it will be used as, and either can be corrected on the spot — there is no separate confirmation screen, because the matching is not a judgement anybody needs to make twice.

This is also the point where a different data source plugs in: give it the same four kinds of file from SAP Readiness Check instead, and everything after this step is unchanged.

There is also a one-click option to use the sample data, so a demo never stalls on a file dialog.

02

See how the system is scored

Your four files become one connected picture: what exists, what calls what, and what is known about each thing. Then every object is scored and given a recommended call.

All of this comes from a rules file you can open and read. Same data in, same answer out, every time.

The step draws it as one strip: the same 106 objects moving through evidence → rule → confidence → the call, so the derivation is visible in the counts rather than asserted. Two real objects are then walked the whole way — one reaching “retire” on a measurement, one reaching “investigate” on an absence, identical until you read the middle. All eleven rules are one click away.

03

See exactly where AI is used

106 custom objects is a list, and nobody funds a list. Grouping them into eleven decisions is done by rule — each object lands in exactly one group, so nothing is counted or paid for twice.

Only then does AI get involved, and only to write words. The step names all three places it does: the summary sentences on each decision, the sentence at the top of the Landscape Footprint, and the assistant. A boundary you can state as a closed list is one somebody can check; one you gesture at is not. The cached text is written once and saved, so the live page never depends on a network connection.

How it actually runs

This is the part to have straight before someone technical asks. Two things happen at the same time; everything after that has to happen in order, because each step needs the answer from the one before it. You cannot score a piece of code before you know what calls it.

What is parallel, and what cannot be

Parallel: the four files are asked for at once rather than one after another, so the slowest one sets the pace instead of the total. On a laptop reading local files the saving is small — 8.7 milliseconds against 9.6 — but the same pattern is what keeps it quick when the files come from somewhere further away.

Sequential: steps 2 to 6 are a chain, and not by choice. Evidence needs the graph, because knowing whether anything still calls a program requires knowing what calls what. Scoring needs the evidence. The rules need the scores. Grouping needs the calls. Trying to run any of it early would mean guessing at the answer it depends on.

What happens when you change the route: not this whole chain. The graph and the scores are worked out once and kept, because which route you take does not change what the data says. Only the last two steps run again, which is why the page responds instantly rather than reloading.

What we know, and what we don't

This is the foundation, and it is the part most tools get wrong. There is a real difference between “we measured this and it never ran” and “nobody measured this”. Treating the second as the first is the quickest way to produce a confident, wrong list of things to delete.

So every object sits in one of four states, and only the first two are actual measurements.

Read those three bars together and the frightening headline turns around. Yes, 175 objects have no usage record — but look where they are. 61% of SAP's own standard code is unmeasured, against 16% of your custom code. The blind spot is almost entirely in code nobody was going to make decisions about anyway. And every single object measured at zero is custom, which is precisely where a retirement list should come from.

How a call is made

No single fact decides anything, because in this data no single fact can. The obvious test for dead code — nothing uses it, it uses nothing, no usage record — returns 105 objects, and 101 of them are SAP's own. It would have been confidently useless.

Instead three kinds of evidence are weighed together.

EvidenceThe question it answers
Does the business use it?Can a person reach it from a menu? How many people, how often?
How tangled is it?What else calls it? Does it write into SAP's own data? Is there a duplicate version?
How old and how neglected?When was it built, when did it last run, who wrote it, are they still here?

The five possible calls

CallWhat it means
RemediateIt writes into SAP's own data. That gets in the way of a clean system, whether or not anyone uses it.
InvestigateThe evidence points in two directions, or it simply is not there yet.
WorkshopThe business clearly relies on it. Whether the new system covers it out of the box is a conversation, not something data can answer.
RetireThe evidence supports switching it off rather than paying to carry it forward.
Carry as-isIt is being used and nothing argues for touching it.
Why Each call also records how solid the evidence behind it is, and that is not decoration. It is a hard limit: “Retire” can only come from a rule resting on a structural fact or an actual measurement. A rule built on inference, or on the absence of a record, proposes “Investigate” instead and names what would settle it. The engine refuses to start if a rule breaks that.

The Discovery Agent

Everything that decides anything here is deterministic, and that has so far been said as a negative: no score, no call and no grouping is written by a model. That proves restraint. It does not show where a model actually pays — and for a capability whose whole premise is that AI is only as good as the context it is given, that is half an answer.

It pays in one specific place. The page in front of a transformation lead carries four files, eleven decisions, five calls, four evidence states and a route lever, and the thing nobody can buy is thirty seconds of an expert saying here is what you are looking at, and here is what I would not trust yet. That is translation, not judgement. It is the right job to give a model and the wrong job to give the rulepack.

So there is a button in the corner of both pages — the Discovery Agent, named for the first of the agent types the Celonis vision paper describes, working in the phase that paper names first: value discovery. On the Extract Wizard it says what just happened to your data and what to know about it before going further. On the Landscape Footprint it says where you stand and how to decide from here.

Written for whom, not how much

One control: for the board, for the programme, for the engineer. Same content, three registers.

It is deliberately not a “less / medium / more” slider. Nobody knows which verbosity they are, but everybody knows which room they are in — and asking for the board version hands you a sentence you can put straight on a slide, live, which is a far better thing to be able to do than to have set detail to medium.

Two rules that keep it honest

It is composed fresh every time it opens, never cached whole. A summary describing the neutral position while the page showed a greenfield reading would destroy the credibility of both. The phrasing is model-written and lives in the file; every number in it is read from your data at the moment you press the button. Switch the route and press it again — the summary moves with the page.

Everything the agent wrote is marked — Discovery Agent generated insight — with what it was written from. A disclaimer says “do not sue us”. Provenance says “here is what to check”, which is the only version worth putting in front of somebody who is about to fund something.

Where it points next

Every held decision already names the one thing that would settle it — a usage collection over a full business cycle, or table row counts from the source system. Read as a sentence that is a caveat. Read as a work order it is something else: scoped, repeatable, with a defined finish line.

That is the shape of work that belongs to an agent rather than a consultant, and the assistant says so: point a collection at the estate, run it for a cycle, re-run this page. The held objects are the backlog it would be handed. Nothing here builds that agent — but the footprint is what would scope it.

The one lever that changes the answer

Which route you take

Rebuild from scratch, convert what you have, or move in slices? It is not settled at this customer, so the tool refuses to assume. The same evidence is read four ways, and the interesting part is where the readings disagree. This is the only control on the page.

RouteWhat rises to the topCode writing into SAP data
No route assumedEverything the extract supports, each decision sized on its own evidenceRemediate
Convert what you haveRetirement first — anything switched off is something you never pay to convert, test and ownRemediate
Build freshEverything actually in use, because nothing carries over by itselfBecomes a spec
Move in slicesThe 18 custom tables — they decide what each slice containsRemediate

Same six objects, opposite meaning. On a conversion they are the hard gate. On a fresh build there is no core to keep clean and nothing to remediate — but those seven write paths describe behaviour the business depends on today, so they stop being defects and become requirements for the thing you are about to build. A tool that had quietly assumed a route would have shown you one of those answers and hidden the other.

What is deliberately not a control

An earlier version of this had a second dial: how much unproven evidence you were willing to act on, nought to a hundred. It has been taken out, and that is a feature rather than a simplification.

No Head of Transformation says “I accept a risk score of seventy”. The dial asked for a number nobody can source, and turning it up far enough made the tool recommend deleting things nobody had measured. A safeguard you can switch off is not a safeguard.

What the dial used to protect is now a property of the engine: nothing is ever retired on evidence weaker than a measurement. The two rules that used to sit behind the dial now propose “Investigate” and name what would settle them, which is what their own wording always said. The default output is identical — only the dial is gone.

Also Whether a missing usage row means “never ran” is a question for the customer's team, not a switch for the reader to guess at. It stays in rulepack.json, stated on the face of the output, and it is one string to change if the answer comes back different.

When you disagree

You can change any recommendation. Open a decision and pick a different call — it is marked edited everywhere it appears, and a Reset to rule proposal button appears next to it.

Three layers, all kept: what the rules proposed from the evidence, what the route you chose implies, and what a person concluded. Each is shown separately rather than collapsed into a single answer.

The original recommendation is never thrown away. The record shows both what the evidence said and what a person concluded, which is the honest way round: the tool is not the decision-maker, but it should not quietly forget that it disagreed.

The answer, first

The Landscape Footprint opens on the thing you actually take to a steering committee. It is the first card on the page, not the last, because a transformation lead should be able to stop reading after it and still have the answer:

“106 custom objects resolve into 11 decisions. 24 of them have an action against them today: 13 retired, 6 remediated to clear the write paths into standard and 5 taken to a fit-to-standard workshop. 31 are held for a named piece of evidence rather than guessed at, and 51 carry forward untouched.”

Underneath it, the whole custom estate drawn as a map: one tile per decision, sized by how many objects it covers and coloured by the call. It answers “what is the split” and “which of these is big” in one picture — a bar chart answers only the first, and would show you 51 objects to carry without showing that 33 of them are one decision and 18 are another resting on completely different evidence. Every tile opens the decision behind it.

Then a line naming exactly what evidence would settle the ones being held, and an export to a text file you can paste straight into a deck. Change the route and the whole card redraws.

Point Most tools answer “what is in your system?”. This one answers “what have you decided, and what are you still not able to decide?” — and it never lets the second one hide.

What it deliberately does not do

Most of what follows was built and then taken out again. That is not waste — a thing you have used for ten minutes tells you something a thing you have only argued about does not, and the fastest way to find out whether a feature earns its place is to live with it. Each of these was removed for a reason worth stating out loud.

Taken outWhy
A risk dial, nought to a hundred It asked for a number nobody can source, and turning it high enough made the tool recommend deleting unmeasured code. What it protected is now a property of the engine: nothing is retired on evidence weaker than a measurement. The default answer did not change.
A switch for “does a missing usage row mean it never ran” A question for the customer's team, not a setting for the reader to guess at. It stays in the rules file, stated on the face of the output, and it is one word to change when the answer comes back.
A browsable list of all 106 objects, with a detail panel per object Built, used, cut. A list of 106 rows is precisely the artifact the eleven decisions exist to replace, and offering one alongside them invites re-litigating the grouping one object at a time. Every object is still there, inside the decision that funds it, with a reason attached.
A risk matrix — criticality against blast radius It restates two numbers as a picture. The decision view already answers the same question with a named rule behind it, which is the part that survives being challenged.
Risk scores on screen “Why is this 72?” costs five minutes of a ten-minute meeting and lands on facts the rule already states in a sentence. The scores still order the rows; they no longer make claims.
A step for confirming which file is which The matching is deterministic — it happens on the way in, by column headings. A whole screen asking someone to confirm a conclusion the tool already reached is ceremony. The override moved onto the file row where it belongs.
A detail slider on the assistant (less / medium / more) Nobody knows which verbosity they are. Replaced with audience — for the board, the programme, the engineer — which is a question anyone can answer instantly.

Also Out of scope on purpose, and sequenced rather than forgotten: a live connection to the source system, the other two productive systems, and agents that act on a decision rather than only proposing it. All three sit in the increment breakdown as Next or Later.

The setting that matters most

One question is still open with the customer: when a piece of code has no usage record, does that mean nobody measured it, or it never ran? It is a switch rather than something buried in code, so the answer costs one edit.

SettingDecisionsWhat unmeasured code getsWhat it means
not measured11Investigate, and say what would settle itThe current assumption. Unmeasured code is never retired.
never ran8Becomes a measurementIf the customer confirms this, unmeasured code becomes evidence, retirement becomes available to it, and three decisions fold into others.

If that question gets answered mid-meeting, absorbing it is a demo asset rather than a setback — it is the same move as any other live change, and it shows the seams hold.
