From one customer’s footprint to a product line

Where the capability goes next — Now / Next / Later, split into what stays custom, what becomes reusable product, and what could stand alone.

NOW
weeks 0–4
 Commit what the evidence supports. Six objects writing into standard finance and sales documents, actionable whether or not anyone runs them. Thirteen retirements on measured evidence. Three transaction codes pointing at programs the inventory does not contain. Freeze the two contracts. The rulepack — every weight in one file — and the four adapter signatures, matched on columns not filenames. The engine already runs headless; this makes it a module, not a demo. — Nothing yet, and resisting the urge is the point: a sample of one is not a product. Instrument instead — every expert override is the signal the rulepack needs, and is already recorded.
NEXT
1–3 months
 Close the evidence gap, then widen the scope. Run SCMON / UPL over a full business cycle so the 34 held objects become decidable — measurement is the only thing that releases them. Recalibrate thresholds against real usage, extend to all three systems, then tie the retirements to test-scope reduction. Read the Context Model where it exists, seed it where it does not. Adapters for SAP Readiness Check and the Custom Code Migration app — and, more importantly, the footprint written back as a technical-layer slice either way, so decisions live where everything else does. A fixed-fee readiness scan. Point it at a prospect’s extract, return a position in days: what is decided, what is held, what it costs to find out. Its honesty about its own limits is what makes it sellable cold.
LATER
3–12 months
 A standing capability, not a one-off study. Continuous re-scoring through cutover: new objects flagged as created, decisions re-opened when their evidence goes stale, progress tracked against the backlog. Agents that act, not only propose. A remediation agent drafting clean-core fixes; a test agent covering what survives. Both hand off through the Orchestration Engine and write back what they did. Decision provenance as a product. The pattern — a call, its evidence, its confidence, and the named thing that would change it — is not SAP-specific. Application-portfolio rationalisation and cloud migration have the same problem.

The line between custom and product

Customer-specific is the rulepack and the narrative: which weights matter here, and the sentences a steering committee reads. Reusable is the engine: adapters, graph, evidence model, scoring. The two never entangle: the engine reads a rulepack it knows nothing about in advance, and the adapters match on structure, not filenames. That is the vision paper’s own argument for the Context Model.

What earns a standalone offering

One correction, made honestly. The footprint runs on a Context Model — the prototype only avoids one by seeding its own slice from four CSVs. A standalone scan is therefore not “the footprint without Celonis”; it is a scan that leaves a Context Model behind. One ending in a PDF is consulting; one ending in a populated technical layer is a land motion.

A capability graduates only when it delivers value before a platform commitment. The readiness scan qualifies: an extract and nothing else, returning a position a sponsor can act on. The evidence-confidence model qualifies differently — decisions carrying their own confidence, naming what would change them, travel far outside SAP. Continuous re-scoring does not: it matters only once you are on the platform.

Where the Discovery Agent goes

The agent shipped in Now reads either page back at the register you pick, every sentence marked and traceable — explanation, not judgement, and deliberately the smallest useful version.

  • Next. Each held decision already names what would settle it — a usage collection, table row counts. A scoped job with a defined finish line is agent work rather than consultant work. The footprint does not run it; it scopes it.
  • Later. The same provenance lets a remediation or test agent hand work back through the Orchestration Engine without losing why a change was proposed. A call that cannot name its rule cannot be handed to an agent safely.

What is deliberately not on this roadmap

A roadmap that only lists additions is a wish list. Three things were built and removed — decided against, not queued:

  • A per-object browser. A searchable list of all 106 objects. It works, and it undercuts the product: the eleven decisions exist to replace exactly that list, and offering it back invites re-litigating the grouping object by object. If a customer insists, the grouping is wrong — not a reason to ship a table.
  • A risk dial. Any control letting a user relax the evidence bar until the tool agrees with them. The bar is a property of the engine, asserted at start-up.
  • Scores and effort estimates on screen. Neither survives challenge — the first invites “why 72?”, the second would be invented from an extract with no size signal. One fabricated number discredits every real one beside it.

Deferred rather than rejected, and sequenced above: a live source-system connection, the other two productive systems, an effort model once source code is in scope, and agents that act rather than propose.

The through-line. One engine, three tiers, three clocks — custom at the customer’s pace, product at the roadmap’s, standalone only when a capability proves itself cold. Separate clocks stop a bespoke script being mistaken for a product, and a genuine product being buried in one account.
What I am not claiming. One of three productive systems, a snapshot rather than a year of observation, a transition type the customer has not settled. Every number is what the extract supports, not a forecast — and nothing is retired on evidence weaker than a measurement, which is why the actionable number is small. The Next column exists because the honest Now is smaller than anyone would like.
