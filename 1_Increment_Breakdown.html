From one customer’s footprint to a product line

Where the Landscape Footprint capability goes next — Now / Next / Later, separated into what stays custom to this customer, what becomes reusable product, and what could eventually stand alone.

Capability: AI System Transformation — Landscape FootprintFrame: Modernize with Celonis Process IntelligenceStatus: prototype on one of three productive systems

The prototype already earns its keep for this customer: it turns a raw metadata extract into eleven funded decisions across all 106 custom objects, each carrying the evidence behind it and how far that evidence goes. The interesting question is what compounds. The three tracks below are the three value tiers the brief asks for, and they deliberately run on different clocks.

NOW
weeks 0–4
 Commit what the evidence already supports. Six objects writing into standard finance and sales documents, actionable today because they hold whether or not anyone runs the code. Thirteen retirements on measured evidence. Three transaction codes pointing at programs the inventory does not contain, as week-one questions. Freeze the two contracts. The rulepack (every weight and threshold in one file) and the four adapter signatures — objects · usage · dependencies · transactions — matched on columns, not filenames. The engine already runs headless; this makes it a module rather than a demo. — Nothing yet, and resisting the urge is the point: a sample of one is not a product. Instrument instead. Every time an expert overrides a call, that is the signal the rulepack needs, and the prototype already records both.
NEXT
1–3 months
 Close the evidence gap, then widen the scope. Run SCMON / UPL over a full business cycle so the 34 objects currently held become decidable — they are held because the engine will not retire anything it cannot point at a measurement for, so measurement is the only thing that releases them; recalibrate the thresholds against their real usage rather than my defaults; extend from one productive system to all three. Then tie the committed retirements to test-scope reduction. Read the Context Model instead of seeding one. Adapters for SAP Readiness Check and the Custom Code Migration app, and — more importantly — write the footprint back as a technical-layer slice so the decisions live where everything else does. Configurable rulepacks per customer. A fixed-fee readiness scan. Point it at a prospect’s extract, return a position in days: what is decided, what is held, and what it would cost to find out. Honest about its own limits, which is what makes it sellable before any platform commitment.
LATER
3–12 months
 A standing capability, not a one-off study. Continuous re-scoring through cutover: new custom objects flagged as they are created, decisions re-opened when the evidence under them goes stale, progress tracked against the committed backlog. Agents that act, not only propose. A remediation agent drafting clean-core fixes for the objects writing into standard tables; a test agent generating coverage for what survives. Both hand off through the Orchestration Engine and write back what they did. Decision provenance as a product. The pattern — a call, its evidence, its confidence, and the named thing that would change it — is not SAP-specific. Application-portfolio rationalisation and cloud migration have the same problem. Plus an anonymised benchmark no single engagement can produce.

The line between custom and product

What is customer-specific is the rulepack and the narrative: which weights, which thresholds, which naming conventions matter here, and the sentences a steering committee reads. What is reusable is the engine: the adapters, the graph, the evidence model, the scoring. The prototype is built so the two never entangle — the engine reads a rulepack it knows nothing about in advance, and the adapters match on structure rather than on this customer’s filenames. That is the same argument the vision paper makes for the Context Model: system-agnostic, composable, decoupled from any one landscape.

What earns a standalone offering

One correction to make honestly. The footprint runs on a Context Model — the prototype only gets away without one because it seeds its own slice from four CSVs. So a standalone scan is not "the footprint without Celonis"; it is a scan that leaves a Context Model behind. That is a better business anyway: a scan that ends in a PDF is consulting, and a scan that ends in a populated technical layer is a land motion.

A capability graduates only when it delivers value before a platform commitment. The readiness scan qualifies: it needs an extract and nothing else, and returns a position a Head of Transformation can act on. The evidence-confidence model qualifies for a different reason — decisions that carry their own confidence and name the evidence that would change them are useful far outside SAP. Continuous re-scoring does not qualify: it only matters once you are already on the platform, so it stays product.

Where the Discovery Agent goes

The agent shipped in Now does one job: it reads either page back to you at the register you pick, and every sentence it writes is marked and traceable. That is deliberately the smallest useful version — explanation, not judgement. The interesting part is what it makes obvious next.

  • Next. Each held decision already names the one thing that would settle it — a usage collection over a full business cycle, table row counts from the source system. That is a scoped, repeatable job with a defined finish line, which is the shape of work an agent takes rather than a consultant. The footprint does not run it; it is what would scope it.
  • Later. The same provenance discipline is what lets a remediation or test agent hand work back through the Orchestration Engine without anyone losing track of why a change was proposed. A call that cannot name its rule cannot be handed to an agent safely.

Naming matters here: it is the Discovery Agent because it works in the phase the vision paper names first, and because calling it anything broader would promise judgement it does not exercise.

What is deliberately not on this roadmap

A roadmap that only lists additions is a wish list. Three things were built during this work and removed, and they are not queued for Later — they are decisions:

  • A per-object browser. A searchable list of all 106 custom objects with a detail panel each. It works, and it undercuts the product: the eleven decisions exist precisely to replace a list of 106 line items, and offering the list back alongside them invites re-litigating the grouping one object at a time. Objects stay reachable inside the decision that funds them, where each carries a reason. If a customer insists, that is a signal the grouping is wrong — not a signal to ship a table.
  • A risk dial. Any control that lets a user relax the evidence bar until the tool agrees with them. The bar is now a property of the engine and is asserted at start-up.
  • Scores and effort estimates on screen. Neither survives being challenged — the first invites “why 72?”, the second would be invented outright from an extract carrying no size signal. One fabricated number discredits every real one beside it.

What is deferred rather than rejected: a live source-system connection, the other two productive systems, an effort model once source code is in scope, and agents that act on a committed decision rather than only proposing it. Those are sequenced above as Next or Later.

The through-line. One engine, three tiers, three clocks. Custom moves at the customer’s programme pace; product moves at the roadmap’s; standalone moves only when a capability can prove itself cold. Keeping them on separate clocks is what stops a bespoke script being mistaken for a product — and what stops a genuine product being buried inside one account.
What I am not claiming. This runs on one of three productive systems, on a snapshot rather than a year of observation, and against a transition type the customer has not settled. Every number above is what the extract supports, not a forecast — and nothing in it is retired on evidence weaker than a measurement, which is why the actionable number is as small as it is. The Next column exists precisely because the honest version of Now is smaller than anyone would like.
